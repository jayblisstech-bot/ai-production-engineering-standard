# APES v1.2.1 — Exact-SHA Production Defaults

## Purpose

v1.2.1 is a release-hardening patch. It does not change the Hermes review engine or severity policy validated in v1.2.0.

The production project template now pins the reviewed APES v1.2.0 runtime commit directly:

`4f02a1ed79fb972998623a62c05a254e0e450687`

Both the reusable workflow reference and `pipeline_ref` use that same 40-character SHA.

## Why

Protected semantic-version tags are useful release markers, but production callers are stronger when they do not depend on any mutable ref at all. Exact commit pinning makes the executed APES runtime content-addressed and auditable.

## Changes

- project template caller changed from `@v1.2.0` to the reviewed runtime commit SHA;
- template `pipeline_ref` changed from `v1.2.0` to the same reviewed runtime SHA;
- reusable workflow default `pipeline_ref` changed to the reviewed runtime SHA;
- workflow contract tests now enforce exact-SHA production defaults;
- onboarding/upgrade guidance now requires the two APES refs to remain identical and SHA-pinned;
- central and project-template version markers bumped to `1.2.1`.

## Runtime provenance

The pinned runtime SHA is the APES v1.2.0 tested release baseline. It previously passed the central 88-test suite and was exercised through live downstream PR integration tests, including fail-closed P0 authorization blocking, corrected-code PASS behavior, exact-SHA caller execution, and Gemini multi-project credential rotation.

Future APES runtime upgrades must be reviewed and tested first, then downstream callers should update both refs to the new reviewed 40-character SHA in a dedicated security-control PR.
